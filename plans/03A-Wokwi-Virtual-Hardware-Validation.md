# 03A — Wokwi Virtual Hardware Validation

STATUS: IN_PROGRESS

## Goal

Add a fast, automated virtual-hardware validation layer for the Rev.1 firmware using Wokwi and the real STM32 build artifact.

This layer sits between host-side unit tests and physical bench qualification:

```text
host unit tests
      |
      v
Wokwi virtual hardware tests
      |
      v
physical bench validation
```

Virtual simulation is a regression tool. It does **not** replace electrical qualification, metrology validation, or safety evidence from the real Rev.1 board.

## Tool decision

Use **Wokwi** as the initial virtual-hardware backend.

Reasons:

- official STM32F103C8 / Blue Pill simulation;
- direct loading of the existing `.elf`, `.hex`, or `.bin` generated by the CMake/Arm GCC build;
- simulated GPIO, USART, SPI, AFIO, RCC, and TIM1/TIM2/TIM3/TIM4 support required by the current firmware foundation;
- built-in ILI9341 simulation;
- deterministic CLI execution suitable for automated tests;
- YAML automation scenarios can drive controls, wait for UART text, and assert GPIO states;
- GitHub Actions integration is available;
- no Arduino, PlatformIO, or alternate firmware architecture is required.

Wokwi is free for personal use but is not an open-source simulator. Wokwi CI is cloud-based, requires a CLI token, and the free plan currently has a finite monthly simulation-time allowance. Automation Scenarios and the Custom Chips API are currently pre-stable APIs, so simulator-version changes must be treated as an external dependency risk.

### Why Renode is not the initial backend

Renode remains a valid future alternative because it is open source, permissively licensed, headless, and has mature Robot Framework integration. However, the current upstream STM32F103 platform description does not provide all peripherals needed by the already-implemented Rev.1 firmware path, especially the SPI/ADC coverage needed for the immediate Phase 03/05 trajectory. Using it now would require more platform/peripheral modeling before it can execute the current firmware meaningfully.

Do not add both simulators at this stage. Keep the test architecture backend-neutral enough that Renode can be introduced later if Wokwi cost, cloud dependency, or simulator limitations become unacceptable.

## Prerequisites

- Phase 01 CMake/Arm GCC build foundation available;
- STM32 Lab or Debug firmware builds successfully;
- Phase 02 safe-boot GPIO/UART foundation implemented;
- Phase 03 digital peripherals implemented at software level;
- current Rev.1 pinout remains authoritative.

This phase may be implemented before Phase 04 and should not change the hardware design.

## Scope

### In scope

- Wokwi project configuration using the real `WTK.RLCMeter.elf`;
- virtual Rev.1 wiring for observable digital interfaces;
- automated UART and GPIO assertions;
- automated button input scenarios;
- timer/PWM output validation where supported;
- SPI/TFT smoke validation;
- a minimal W25Q64 simulation model if required for meaningful Flash-driver testing;
- virtual quiet-mode regression tests;
- CI-ready commands and GitHub Actions integration;
- explicit separation of host, virtual, and bench evidence.

### Out of scope

- claiming real electrical safety from simulation;
- relay contact resistance/bounce validation;
- analog AFE accuracy/noise/phase modeling;
- MCP6002 electrical modeling;
- real battery/charger behavior;
- ADC2/DMA metrology qualification;
- EMI/crosstalk;
- residual high-voltage qualification;
- CAT rating or energized-mains measurement claims;
- replacing Phase 09 bench validation.

## Known simulator limits

At plan creation, Wokwi's STM32F103C8 model supports the processor core, SysTick, GPIO, USART, I2C, SPI, STM32 timers, EXTI, RCC, AFIO, and GDB debugging. ADC support is limited to basic ADC1 conversion; ADC2 is not implemented. DMA and IWDG are not implemented.

Therefore:

- Phase 02/03 digital behavior is a strong initial target;
- portions of Phase 04 can be exercised through digital inputs/policy, but analog safety thresholds remain host/bench territory;
- Phase 05 deterministic ADC1+ADC2/DMA acquisition cannot be qualified in Wokwi;
- watchdog behavior remains bench-only unless the simulator gains IWDG support.

Document simulator limitations in every virtual-test handoff. Do not silently convert unsupported hardware behavior into fake mocks that imply qualification.

## Canonical firmware artifact

Simulation must execute the same firmware produced by the normal STM32 build.

Preferred initial artifact:

```text
Firmware/build/stm32-lab/WTK.RLCMeter.elf
```

Canonical build:

```bash
cd Firmware
cmake --preset stm32-lab
cmake --build --preset stm32-lab
```

`wokwi.toml` must point at the generated ELF rather than maintaining a separate Arduino, PlatformIO, CubeIDE, or simulator-specific firmware project.

A simulator-only target may be introduced only if a concrete emulator limitation requires it. If introduced, it must compile the same production sources and must not change safety policy or application behavior merely to make tests pass.

## Test philosophy

Prefer black-box observations of the real firmware:

- GPIO levels;
- UART diagnostics;
- button-driven behavior;
- SPI transactions;
- display behavior;
- PWM/timer output.

Do not expose internal state solely because it is convenient for simulation when the same behavior can be tested externally.

If a test-only diagnostic hook becomes necessary:

1. keep it behind an explicit Lab/virtual-test compile-time option;
2. do not compile it into Release;
3. do not bypass safety policy;
4. document why external observation was insufficient;
5. make the hook deterministic and narrow.

## Task 1 — Establish Wokwi project

Create `Firmware/sim/wokwi/wokwi.toml` and `diagram.json`.

The diagram must use the STM32F103C8 Blue Pill and mirror the authoritative Rev.1 digital pinout needed by current tests.

Initial required observable nets:

```text
PA8   PWM_EXC
PA9   DEBUG_TX
PA10  DEBUG_RX
PA11  K2_CMD
PA12  FLASH_CS
PA15  CHG_DETIO
PB0   TFT_BL
PB1   IO_BUZZ
PB3   SW_UP
PB4   SW_DOWN
PB5   RANGE_A0
PB6   RANGE_A1
PB7   RANGE_A2
PB8   RANGE_EN
PB9   K1_CMD
PB10  TFT_RST
PB11  TFT_DC
PB12  TFT_CS
PB13  TFT_SCK
PB14  TFT_MISO
PB15  TFT_MOSI
PC13  SW_OK
```

PA13/PA14 remain SWD and are not reassigned.

## Task 2 — Boot-safe scenario

Create the first mandatory automated scenario proving safe digital defaults after reset.

At minimum verify, after firmware boot reaches a defined observable point:

```text
PA8   PWM_EXC   = inactive
PA11  K2_CMD    = de-energized
PB8   RANGE_EN  = disabled
PB9   K1_CMD    = de-energized
PB1   IO_BUZZ   = inactive
PA12  FLASH_CS  = inactive/high
PB12  TFT_CS    = inactive/high
```

Also verify the UART reports the expected boot identity/state.

This is a regression assertion only. It does not prove relay or analog hardware safety.

## Task 3 — UART boot diagnostics

Automate validation of stable boot diagnostics emitted on USART1.

Verify at least:

- product identifier;
- firmware/build identification where deterministic;
- clock source/status;
- SWD preservation indication;
- safe boot state;
- SPI/W25Q/display initialization outcome appropriate to the simulated peripherals.

Avoid matching volatile Git hashes or build strings unless the scenario intentionally supplies the expected value.

## Task 4 — Button scenarios

Connect three virtual pushbuttons to the real Rev.1 button pins and automate:

- UP press/release;
- DOWN press/release;
- OK press/release;
- long OK;
- button bounce/debounce smoke behavior if controllable at the scenario level;
- repeated press behavior where useful.

Prefer verifying UART event diagnostics initially rather than implementing final Phase 08 navigation early.

## Task 5 — Backlight and buzzer timing

Validate digital/timer behavior supported by the simulator:

- PB0 backlight PWM is generated at the configured baseline frequency;
- duty changes are observable;
- PB1 buzzer can produce approximately 500 Hz, 1 kHz, and 2 kHz test tones;
- entering peripheral quiet mode stops/mutes the buzzer and prevents a new tone from starting;
- backlight remains stable during quiet mode according to the architecture contract.

Use Wokwi's virtual logic analyzer/VCD output where scenario-level assertions cannot directly measure frequency/duty.

Any tolerance must account for simulator representation but remain tight enough to catch timer configuration regressions.

## Task 6 — ILI9341 smoke validation

Use Wokwi's built-in ILI9341 model with the Rev.1 SPI2/control wiring.

Validate at least:

- reset/init reaches ready state;
- CS and DC wiring is correct;
- RGB565 test colors render correctly;
- basic procedural/fallback text path executes;
- no full framebuffer is introduced for simulation convenience.

If screenshot comparison is stable enough for CI, add one small deterministic screenshot smoke test. Otherwise keep display acceptance based on UART/state and SPI evidence and reserve visual fidelity for manual/bench validation.

## Task 7 — Shared SPI ownership

Exercise the shared SPI2 architecture with TFT and Flash chip-selects.

Required invariant:

```text
TFT_CS == LOW and FLASH_CS == LOW
```

must never occur simultaneously.

Prefer an automated assertion or an analyzer post-processing test that fails on overlap.

Also verify idle-high behavior for both chip selects.

## Task 8 — W25Q64 virtual model

If required, implement the smallest deterministic W25Q64 model needed by the current driver.

Initial command set:

```text
0x9F  JEDEC ID
0x05  Read Status Register 1
0x06  Write Enable
0x03  Read Data
0x0B  Fast Read
0x02  Page Program
0x20  4 KiB Sector Erase
```

Baseline JEDEC response for the intended W25Q64 family must match the driver's supported table.

Model only behavior that the firmware actually relies on. Do not attempt to reproduce every Winbond feature in this phase.

Required scenarios:

- Flash present and recognized;
- wrong manufacturer/JEDEC rejected;
- normal bounded read;
- page program + readback;
- sector erase + readback;
- BUSY behavior long enough to exercise start/poll logic;
- Flash absent/failure degrades UI/resource capability without changing safety GPIO behavior.

The W25Q custom-chip code is simulator infrastructure, not target firmware, and may use the language/tooling required by Wokwi's Custom Chips API.

## Task 9 — Quiet-mode integration scenario

Create an integration scenario that starts noncritical peripheral activity and then requests the existing peripheral quiet contract.

Verify:

- no new TFT transaction starts while quiet is active;
- no new W25Q transaction starts while quiet is active;
- resource streaming preserves its offset/state when deferred;
- buzzer becomes inactive;
- releasing quiet permits later activity to resume;
- no safety GPIO changes as a side effect.

Do not implement Phase 05 acquisition merely to trigger quiet mode. A narrow Lab diagnostic command is acceptable if required and explicitly isolated from Release.

## Task 10 — Phase 04 virtual safety scenarios

Once Phase 04 exists, extend the same virtual platform instead of creating a new simulator project.

Digital/policy scenarios should include:

```text
charger present -> MEASURE denied
invalid sensor/policy state -> MEASURE denied
range transition -> RANGE_EN low while address changes
fault -> excitation off and K1 SAFE
reset during activity -> returns to safe digital defaults
```

Analog values injected into basic ADC1 simulation may be used only for software-policy regression where the simulator supports the exact channel behavior. Do not treat these tests as divider, ADC, residual-voltage, or metrology qualification.

## Task 11 — CLI wrapper

Provide a repository-local wrapper so developers and agents do not need to remember Wokwi command details.

Preferred interface:

```bash
cd Firmware
./tools/run_virtual_tests.sh
```

or an equivalent cross-platform Python wrapper if Windows/Linux portability is materially better.

The wrapper should:

1. verify the expected ELF exists or build it when explicitly requested;
2. verify `wokwi-cli` is available;
3. verify the required token exists without printing it;
4. run all scenarios with bounded timeouts;
5. return nonzero on any failure;
6. keep logs/artifacts in a predictable ignored build/output directory.

Do not download/execute arbitrary installer scripts automatically from the test wrapper.

## Task 12 — GitHub Actions

Add a dedicated virtual-hardware workflow after local CLI validation is stable.

Requirements:

- build `stm32-lab` using the existing CMake flow;
- run a short virtual smoke suite automatically;
- use `WOKWI_CLI_TOKEN` from GitHub Actions secrets;
- never print the token;
- set strict per-scenario timeouts;
- upload useful logs/VCD/screenshots only on failure or when diagnostically valuable;
- keep total simulator time low enough to respect the current free-plan monthly allowance;
- allow `workflow_dispatch` for the complete suite.

Recommended policy while the free allowance is limited:

```text
Pull request / main push:
    short boot-safe + UART + button + SPI-CS smoke suite

Manual workflow_dispatch / release candidate:
    full virtual suite
```

If monthly limits become operationally restrictive, reassess Renode or another self-hosted/open-source backend rather than weakening test coverage silently.

## Task 13 — Evidence classification

Every relevant plan/handoff should distinguish:

```text
HOST_TESTED
VIRTUAL_HARDWARE_TESTED
REQUIRES_BENCH_VALIDATION
BENCH_VALIDATED
```

Virtual success may remove software uncertainty, but it must never remove a bench requirement involving:

- analog values;
- electrical timing/signal integrity;
- real relays/transistors;
- power rails;
- thermal behavior;
- high voltage;
- metrology accuracy;
- ADC/DMA behavior unsupported by the simulator.

## Automated acceptance criteria

This phase is software-complete when:

1. the standard STM32 Lab ELF boots in the simulator without a simulator-specific firmware fork;
2. one command runs the complete local virtual suite unattended;
3. process exit status is nonzero on a deliberately broken expectation;
4. boot-safe GPIO assertions pass;
5. UART boot scenario passes;
6. all three button inputs can be driven automatically;
7. backlight/buzzer digital timing has automated evidence where supported;
8. ILI9341 initializes in simulation and executes the RGB565/fallback rendering smoke path;
9. TFT/Flash CS overlap is automatically rejected;
10. W25Q driver behavior is exercised against a deterministic simulated target or an explicitly documented reduced substitute;
11. quiet-mode regression passes;
12. no production safety policy is bypassed for simulation;
13. host tests and normal STM32 Debug/Release/Lab builds remain green;
14. README documentation explains install, local execution, CI execution, limitations, and troubleshooting.

## Bench acceptance impact

No existing bench requirement becomes COMPLETE merely because this phase passes.

Instead, Phase 02/03/04 handoffs may add virtual evidence such as:

```text
Safe GPIO boot logic:          VIRTUAL_HARDWARE_TESTED / REQUIRES_BENCH_VALIDATION
SPI ownership logic:           VIRTUAL_HARDWARE_TESTED / REQUIRES_BENCH_VALIDATION
Button application behavior:   VIRTUAL_HARDWARE_TESTED / REQUIRES_BENCH_VALIDATION
Buzzer timer programming:      VIRTUAL_HARDWARE_TESTED / REQUIRES_BENCH_VALIDATION
```

Physical behavior remains a separate gate.

## CI cost/time budget

The implementation must report measured virtual simulation time for the smoke and full suites.

Keep test scenarios focused. Do not waste simulated seconds waiting for long human-visible delays when the same state can be asserted deterministically sooner.

Target initial budgets:

```text
smoke suite:  <= 30 simulated seconds total
full suite:   <= 120 simulated seconds total
```

These are planning targets, not acceptance claims; revise them after actual measurement.
