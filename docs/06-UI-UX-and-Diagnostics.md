# UI, UX, and Diagnostics

## October24 integration baseline

The owner-confirmed mounting is portrait180 (240x320,MADCTL88,rotation2). All TFT-bearing profiles now share50ms reset/250ms release wait and PCLK1/64 TFT clock; Flash stays/8. White screen was a module flat solder fault, repaired by the owner. Rendering/buttons/tones are functionally confirmed; exact controller ID and full resource/storage/quiet bench qualification remain open.

See [current evidence, input limits and release status](review/bringup-2026-10-24/README.md).

## Display

Controller: ILI9341, 240×320, SPI.

Primary pixel format: RGB565.

A full RGB565 frame requires:

```text
240 * 320 * 2 = 153600 bytes
```

This exceeds the available RAM on the STM32F103C8T6, so the UI uses incremental rendering and streaming rather than a full framebuffer.

## UX principle

Normal use should not require navigating a menu or selecting whether the DUT is a resistor, capacitor, or inductor.

The default interaction is:

```text
connect DUT
    ↓
short OK
    ↓
automatic measurement / autorange / classification
    ↓
result pages
```

The metrology core always determines complex impedance first. Component classification is a later interpretation of the measured result and its behavior across available measurement conditions. The normal product UI therefore does not ask the user to preselect R, L, or C.

A future/manual laboratory measurement mode may expose frequency/range/amplitude controls, but it is not part of the normal Rev.1 navigation contract.

## External resource ROM

The W25Q Flash is the external resource/data ROM for the instrument, not merely an image store.

Resources may include:

- rasterized custom fonts and glyph metrics;
- large numeric glyph sets;
- measurement symbols such as Ω, µ, °, and ±;
- icons and small graphical resources;
- localized UI strings/resources where practical;
- optional bitmaps;
- calibration/settings/diagnostic records in separately managed storage regions.

Authoring fonts such as TTF/OTF are converted offline on the development PC into a compact MCU-oriented format. The STM32 does not parse TTF/OTF and does not embed a desktop font engine such as FreeType.

Runtime rendering uses fixed, small buffers:

```text
W25Q -> small fixed RAM scratch buffer -> ILI9341
```

Installed font/resource size must not cause proportional SRAM consumption. A few hundred bytes is the preferred initial scratch-buffer target; a larger value requires measured justification.

The product fallback renderer is cooperative. It pauses during quiet mode, draws text in
bounded character steps, and updates only the affected product result/body region when a
new snapshot arrives on the same page. Full-screen clears are reserved for first render
or state/page transitions. The UI model stores a compact presentation snapshot, not the
complete measurement-session result.

A minimal emergency font remains in MCU internal Flash so fundamental safety/error messages can still be shown if W25Q resources are unavailable or corrupt.

Procedural graphics such as lines, boxes, scales, graphs, vectors, component symbols, and equivalent-circuit drawings should normally be generated by code rather than stored as full-screen images.

Resource Pack v2 API version 4 is the current product text/font contract. English and
Portuguese (Brazil) catalogs must provide dense text IDs `0x0001..0x0059`, every string
must fit the 31-byte line contract, and firmware validates both languages before
admitting the pack. `FONT_UI_SMALL`, `FONT_UI_MEDIUM`, and `FONT_UI_LARGE` are required
`FONT_BITMAP_A1_V1` resources with explicit 32-byte headers, sorted 20-byte glyph
records, row-major MSB-first A1 bitmaps, 32x32 maximum glyph geometry, and required
coverage for current catalog text plus technical symbols such as `Ω`, `µ`, `°`, `±`,
and `·`.

Technical tokens such as frequency labels, amplitude labels, range names, percentages,
seconds, punctuation, hex digits, and `n/a` may remain firmware-local formatting
literals, but normal PRODUCT rendering uses external font resources. Emergency
`RESOURCE_ERROR` and fault text remains on the internal fallback renderer.

Current product typography is offline-rasterized IBM Plex Sans (small/medium) and
IBM Plex Mono (large numerics), including eight menu icon glyphs. The READY page has
optional wordless 240x320 RGB565 RLE art in W25Q. Localized labels and changing values
are composed by firmware over the art; no language or measurement value is baked into
an image. Corrupt/missing optional art leaves the functional text page intact. Required
catalog/font failure keeps the internal bilingual PC-link recovery screen available.
The reviewed host-rendered EN/PT-BR contact sheets are
`Firmware/renders/product-ui-en-pt.png` and
`Firmware/renders/product-ui-en-pt-secondary.png`, with blank-W25Q recovery in
`Firmware/renders/product-ui-en-pt-recovery.png`; physical contrast and readability remain
`REQUIRES_BENCH_VALIDATION`.

## Measurement result pages

The experimental `WTK_PRODUCT_FACTORY_PROVISIONED=ON` implementation is specified
and tested in [C03.1](review/c03/README.md). Its primary page shows R/C/L or complex
impedance interpretation, selected frequency/amplitude, provisional signal
confidence and explicit unknown maximum error. Details show R(AC), X, |Z|, phase,
applicable ESR(AC)/Q/D and selected RREF/return path/attempt count. Numerical values
require compatible persisted OSL, valid source evidence and an applicable model;
unavailable values show `n/a`. AC series loss does not claim DC winding resistance.

In that experimental mode, UP/DOWN wrap primary/details; short OK in details
returns READY, short OK in READY/primary requests one measurement, and short OK
while measuring cancels. PARTIAL is explicit. A new request, safety/resource
interruption or calibration revocation clears the old snapshot. Boot never starts
measurement automatically. Valid results state `Max error: not characterized` /
`Erro max.: nao caracterizado`; qualified numerical bounds require a future
compatible physically qualified evidence reader. The legacy default retains its
existing wizard and result interaction. No Resource Pack wire or text-ID change.

UP and DOWN navigate the pages of the last measurement result. Pages should wrap or stop consistently; the final interaction policy is frozen during implementation, but UP/DOWN must never change metrology parameters while the user is browsing normal result pages.

Pages that do not have meaningful data for the current result may be omitted.

### Page 1 — Primary result

The primary page is intentionally minimal and uses large typography.

It shows at least:

- automatically detected dominant component/model, when classification is valid;
- primary value and SI unit/prefix;
- battery state/status as appropriate;
- small measurement-condition metadata in the lower area.

The lower metadata should identify the excitation amplitude and frequency that most directly support the displayed primary value, for example:

```text
100 mV · 1 kHz
```

If multiple frequencies were used for classification or confidence checks, the footer must not imply that they were unused. The detailed/technical page exposes the complete attempt/condition history or summary.

Representative layout:

```text
┌──────────────────────────────┐
│ WTK RLC                82%   │
│                              │
│          CAPACITOR           │
│                              │
│          1.002 µF            │
│                              │
│                              │
│                 100mV · 1kHz │
└──────────────────────────────┘
```

### Page 2 — Electrical details

Show only quantities that are meaningful for the selected equivalent model and confidence level.

Potential values include:

- R and X;
- `|Z|` and phase;
- ESR;
- Q;
- D;
- winding/series resistance;
- series-equivalent C or L;
- confidence/status.

The current PRODUCT detail page renders AC R (labeled ESR for a capacitive
model with nonnegative series real part), X, |Z|, and phase. Invalid DSP
quantities render `n/a`. ESR is the series AC real component at the displayed
measurement condition, not a DC winding resistance or a datasheet ESR at an
unmeasured frequency. Q and D are already derived by the DSP when valid but
are not yet published on this page; the internal-Flash budget remains a gate.

Do not display invalid derived quantities as plausible numbers. Use an explicit unavailable/not-applicable indication where required.

### Page 3 — Measurement information

Engineering metadata may include:

```text
primary frequency
primary excitation amplitude
RREF
RET channel strategy
confidence class/reasons
frequencies used for classification/refinement
number of attempts/retries
```

Bringup/Debug builds may expose additional acquisition detail.

### Graph/result pages

Useful graph pages may include, when supporting data exists:

- impedance magnitude versus frequency;
- phase versus frequency;
- R/X or complex-vector visualization;
- equivalent electrical model drawn procedurally;
- comparison of 100 Hz / 1 kHz / 10 kHz results;
- component-specific derived visualizations supported by measured data.

Graphs must communicate measured or explicitly derived information rather than serve as decoration.

A calculated capacitor charge/discharge curve, if retained, is a derived visualization and must not be described as a captured transient waveform.

## Measurement-in-progress presentation

A short OK press from the normal result/home context requests a new measurement.

While the measurement engine is working, the display should provide useful progressive feedback rather than remain static. The large central value may be updated with valid partial/refined results as they become available, together with a clear waiting/progress indication such as:

```text
Please wait...

1.001 µF

checking ESR...
```

or equivalent localized wording.

The progress presentation may communicate states such as:

- probing;
- refining range;
- checking another frequency;
- calculating ESR/Q/D;
- finalizing confidence.

However, TFT/Flash activity must not compromise metrology timing or quiet-mode behavior. The UI is updated **between** critical acquisition windows:

```text
ACQUIRE
    ↓
PARTIAL PROCESS
    ↓
UI UPDATE
    ↓
NEXT ATTEMPT / ACQUIRE
```

Do not continuously redraw the TFT from inside the ADC/DMA critical acquisition window. The displayed intermediate value must be based on a completed valid partial measurement, not raw individual ADC samples presented as a result.

## Button contract

Three buttons:

- UP;
- DOWN;
- OK.

The button driver emits debounced press/release/long/repeat events. Screen/navigation policy belongs above the driver.

### Normal measurement/result context

```text
OK short     request measurement
UP           previous result page
DOWN         next result page
OK long      open main menu
```

Long UP/DOWN may repeat navigation where useful but must not create hidden metrology configuration changes.

### Menu context

```text
UP           previous item / increase value
DOWN         next item / decrease value
OK short     select / confirm
OK long      back
```

Avoid making button combinations, double-clicks, or triple-clicks part of ordinary operation. Such combinations may be reserved for controlled service/debug functions only if later documented.

### Backlight-off behavior

When the backlight has timed out and is fully off, the first button press wakes the display and is consumed. It must not simultaneously start a measurement, change a setting, or activate a menu item.

## Calibration

Calibration has two entry paths:

1. mandatory boot-time calibration when valid calibration data is absent or incompatible;
2. explicit user entry through the Calibration menu after a valid calibration already exists.

The Calibration menu/wizard provides OPEN/SHORT/LOAD procedures and calibration status/information.

A manually started recalibration must not destroy the currently valid calibration before the replacement has been completely written and verified.

Phase 08 Stage 2A implements the first product calibration path with a deliberately
narrow menu subset:

```text
Calibration
Back
```

The full Display/Sound/Language/Diagnostics/Maintenance/About menu was staged after
the initial Stage 2A executable subset. The Calibration entry shows active/required
status and starts the full range-batched OSL wizard.

Maintenance is the user-visible service entry point for non-measurement tasks such as
PC-link resource provisioning and future settings/service tools. The initial PC-link
contract is a framed protocol for Resource Pack transfer and validation; it is not a
replacement for menu-driven calibration. UART may carry service data when explicitly
requested, but ordinary measurement, calibration, settings, and safety flows must remain
usable from the product UI. The first executable Maintenance UI is a submenu with PC
Link and Resources status pages only; enabling a write/commit action requires a later
explicit service-flow stage.

The wizard flow is:

```text
intro
for each range:
    connect OPEN fixture once
    capture all calibratable conditions for that range
    connect SHORT fixture once
    capture all calibratable conditions for that range
    connect LOAD fixture once
    capture all calibratable conditions for that range
    solve records for the range
confirm save
commit/verify W25Q candidate
activate
complete
```

There is no OK confirmation per frequency/amplitude condition. Progress screens expose
the current range, fixture, condition index, frequency, amplitude, accepted sample count,
and save/commit state.

If storage is unavailable, calibration acquisition does not start. If safety blocks a
fixture capture, the wizard waits in a safety-blocked state and no Phase 05 transaction
is requested. Manual recalibration keeps the previous valid active set until the new
candidate has been committed and verified.

Fault presentation is intentionally decoupled from physical teardown. The PRODUCT UI may
show `FAULT`, `CALIBRATION_REQUIRED`, `CANCELING`, or storage-error states immediately,
but the application keeps stepping the active measurement or calibration runtime until
Phase 05 has stopped ADC/DMA/excitation, returned K1 SAFE through its owner, acknowledged
the transaction, and released the shared workspace. UI state must not cause the runtime
union or raw workspace to be reused early.

Calibration wizard diagnostics expose the latest solved condition's OPEN, SHORT, and
LOAD temperatures plus min/max/span. These values are provenance only; no temperature
span rejection threshold is implemented before bench evidence.

## Mandatory calibration gate

On every boot the application validates persisted calibration before entering normal measurement-ready state.

Validation includes, as applicable:

```text
record magic/type
schema/model version
hardware revision compatibility
bounds/length
CRC/integrity
required calibration-set completeness
```

Boot policy:

```text
BOOT / SELF TEST
    ↓
load and validate calibration
    ↓
valid? ── yes ──> normal READY
   │
   no
   ↓
CALIBRATION_REQUIRED
    ↓
Calibration wizard
    ↓
write candidate
    ↓
read-back / CRC / completeness verify
    ↓
activate
    ↓
READY
```

When calibration is missing, corrupt, incomplete, or incompatible, the user is forced into the Calibration flow and cannot enter normal measurement-ready operation until a valid required calibration set exists.

Calibration persistence belongs to the W25Q storage architecture. The STM32F103C8T6 does not provide native EEPROM; do not describe this storage as MCU internal EEPROM.

## Display menu

Planned settings:

- brightness;
- backlight timeout.

Backlight timeout may include an always-on option plus practical timeout choices. Turning the backlight off does not by itself imply powering down the instrument.

PB0 controls brightness through PWM. PWM behavior during metrology quiet windows must follow the validated noise policy.

## Sound menu

The Sound menu provides at least a persistent user enable/disable setting for ordinary buzzer feedback.

Potential ordinary feedback includes:

- button confirmation;
- valid measurement completion;
- invalid action;
- calibration completion.

The policy for safety-critical audible alerts versus the user Sound setting must be explicitly decided and documented before release rather than assumed silently.

The passive piezo is mounted externally in the enclosure. PB1 drives a BC817 low-side switch. The buzzer is muted during critical metrology acquisition.

Initial planned languages:

- Português;

## Debug menu and console

The Debug menu may expose:

- console enable/disable;
- log level;
- live/system diagnostics;
- measurement dump controls;
- storage/peripheral status.

When the on-screen debug console is enabled, it becomes an additional page in the normal UP/DOWN result-page sequence.

The TFT console is a bounded recent-event view backed by a fixed-size ring buffer. It is not a full history log and must not grow dynamically.

Representative display:

```text
DEBUG CONSOLE
128.341 MEAS start
128.342 RREF=1k
128.344 FREQ=1kHz
128.392 ADC done
128.398 Z=0.83-j158.9
128.399 class=CAP
128.401 conf=0.98
```

UART remains the higher-volume diagnostic stream. Bringup and host diagnostic tools may emit detailed per-measurement dumps including attempt conditions, raw statistics, phasors, complex impedance, calibration IDs/coefficients, confidence reasons, classification, and rerange/retry reasons.

Logging must respect quiet mode and must not perform high-volume output inside critical ISR/acquisition paths.

Phase 07 automatic-session policy and orchestration are product application services
with host-tested diagnostics. The STM32 Bringup console is intentionally limited to
hardware bring-up, raw metrology capture, sensor, storage, and calibration commands so
Release/Product builds do not carry rich automatic-measurement presentation strings.
Future Phase 08 UI work may display automatic-session events such as `AUTO_BEGIN`,
`ATTEMPT_BEGIN`, `PARTIAL_RESULT`, `FINAL_RESULT`, and `AUTO_END` through product UI or
host-side tooling outside critical acquisition windows.

## Safety/UI priority

Safety warnings and mandatory boot gates override ordinary navigation.

The UI must never directly operate K1, K2, RANGE_EN, or excitation GPIOs. It emits user intent; application/hardware services decide whether the requested action is allowed.

## Shared boot splash (2026-10-24)

Every embedded profile, including BRINGUP_CAL and peripheral/relay/bench variants,
uses the same optional owner-supplied 240x320 W25Q image at resource ID 0x00030006.
The existing READY artwork remains separate. Initialization and incremental CRC/
RLE validation precede streaming; each validation call reads at most 128 bytes and
each TFT draw/clear call sends at most 64 pixels. No framebuffer or heap is added.
The completed image is held for 3000 ms, measured from the following loop after the
last pixel transfer; unsigned elapsed time handles millisecond wraparound.

Sensors, watchdog and SAFE policy continue throughout presentation. Normal UI,
serial commands, capture, relay pulses and persistent mutations wait. Failed or
absent assets/display skip the optional phase; wait/validation/draw has a 15000 ms
budget, hold is 3000 ms, and clear has its own 15000 ms budget. Safety faults or quiet
requests abort immediately. Display orientation remains rotation 2. BRINGUP_CAL
returns to its existing binary-only service after its boot-only graphics phase.
See [asset provisioning](../Firmware/assets/README.md) for the updated procedure.
Visual appearance and visible timing require observation on the connected TFT.


## Incremental factory menus (2026-10-26)

PC-provisioned PRODUCT enables exact completed-row caching for the main,
display/brightness/timeout, sound, language and maintenance menus, plus normal
diagnostic/status/about screens. Navigation repaints only
the old/new highlighted rows; a numeric edit repaints its changed row. The
cache stores text, color, position, extent and font mode for nine completed
rows plus one in-flight row; there is no screen framebuffer. A shorter value
or removed save-warning row is erased over its old full row extent.

Generation updates during a glyph or row clear converge on the newest view.
Only completed glyph rows enter the cache. Quiet suspends both clear and text
steps. Font/resource mode changes repaint affected rows; language and screen
transitions rebuild the baseline. A failed clear/glyph invalidates the cache
and forces recovery from a full baseline. READY's fixed-background coalescing
and other result/page transitions are preserved. Numeric redraws do not add
settings writes; existing editor save/confirm/cancel policy remains in charge.

The full embedded-wizard PRODUCT retains its prior bounded renderer to fit the
existing Flash gate. Both profiles gain correct full language-change recovery,
including the bottom READY hint, and invalidation after failed painting. Display
transfer-count tests cover the incremental behavior; physical appearance and
button responsiveness await owner validation because TTL occupies the display
connection during unattended work. See
[plan 24](../plans/24-Measurement-Evidence-Session-and-UI.md).

A custom medium font taller than the 28-pixel minimum menu row pitch uses a
full repaint so clearing one row cannot damage cached neighbors. Provider
invalidation is honored even when the view generation has not changed.

## Trimmed-result details

Factory PRODUCT details append AVG7/3 only after seven valid calibrated complex
samples have completed coordinate-wise two-per-tail trimming and SAFE cleanup.
The adjacent attempt count remains the raw autorange-condition count; it does
not include the six or up-to-eight extra statistical windows. Diagnostic session
metadata carries admitted/extra counts, independent R/X retained masks and all
seven raw complex points. An incomplete or hardware-aborted collection is not
presented as an averaged measurement. No asset-pack or persistent-settings update
is needed for this indicator.

## Frequency-survey coverage

Factory continuous relay/power ownership is defined by plan 27. The following
frequency and seven-point UI metadata remains unchanged.

Factory PRODUCT details append F<n>/3 for attempted frequency coverage, alongside
AVG7/3 for a successfully completed primary-condition estimator. Separate raw
attempted/usable masks remain in diagnostic result metadata; F3/3 does not claim
three usable/qualified observations or absolute accuracy. Low-frequency surveys
can take seconds and intentionally use SAFE/fresh-permit relay boundaries.
Below the ~1-ohm lower engineering target, resistance-dominated uncertain data
uses IMPEDANCE/unknown instead of asserting RESISTOR. No asset-pack change is
required for these compact indicators.

## Serial short-OK control

WTK_ENABLE_SERIAL_UI is a CMake option, ON by default for PRODUCT. It enables
existing PLC1 receiving in Debug as well as Release/factory PRODUCT. BRINGUP
and BRINGUP_CAL retain their diagnostic protocols; neither has the product UI
OK action. Their capture commands are not aliased to a relay shortcut. Setting
-DWTK_ENABLE_SERIAL_UI=OFF removes serial UI control without disabling safety.

Use Firmware/tools/pc_serial_ui.py --port COM4 --out <new-directory> for a
read-only state query; add --ok for one explicit short click after a fresh query.
115200 8N1 and deasserted DTR/RTS are shared with existing tools. A timeout is an
ambiguous activation outcome; the client never retries. Inspect state/results
before explicitly sending another request. WOKE_ONLY reports a complete first
click consumed by backlight wake, without starting acquisition. This preserves
physical-button behavior. Acceptance is not a measurement-completion reply.

PLC1 request types 0x30 (status) and 0x31 (short OK) have exactly 12 payload bytes:
API u8=1, echoed command u8, reserved u16=0, nonzero increasing request ID u32,
expected measurement-session sequence u32, all little-endian. Header sequence
matches the low 16 ID bits; flags must be zero. Payload CRC, command echo and
identity must match. Status ignores the expected sequence; activation requires
an exact match. Rejected valid IDs are consumed, so commands cannot wait for
later admission. No activation replay is allowed within a boot. The tool uses
fresh increasing IDs and records exact request/reply bytes.

Response type 0xB0 has 16 payload bytes: API u8, echoed command u8, status u8,
UI state u8, request ID u32, current session sequence u32, safety blocker flags
u32. Status values are ACCEPTED=0, BAD_REQUEST=1, STALE_REQUEST=2,
SESSION_MISMATCH=3, NOT_READY=4, SAFETY_BLOCKED=5, WOKE_ONLY=6. Request IDs are
boot-local and must increase without wrap; they are not authentication tokens.
Only initialized READY/RESULT presentations can accept a short click. Actual
hardware must be SAFE, range disabled, source OFF, idle/free of metrology and
resource ownership, with no charger/fault/supply/residual blocker and active
calibration. Physical-button/pending UI overlap is rejected. The usual app and
hardware fresh-permit checks still run after the ordinary PRESS/RELEASE pair.
No menu confirmation, calibration action, long press, repeat or raw GPIO control
is provided. Queries do not wake or start measurement. Quiet acquisition defers
UART parsing/output and discards partial frames; partial RX expires at 250 ms.
Resource payload bytes are never scanned as UI commands.

## Production completion: native lead compensation

With valid factory calibration and the lead service attached, selecting Calibration opens the lead menu directly. `New OPEN/SHORT` asks for OPEN at the final lead tips, then a firm SHORT at those same tips. Discharge/remove all DUTs and independent sources first. Each endpoint captures seven coherent windows at 10 Hz, 1 kHz and 10 kHz; no LOAD resistor is requested. Standard changes occur only after complete hardware teardown. Review -> short OK saves the candidate; holding OK cancels before saving. A committed save cannot be undone by cancellation. Enable/disable retains coefficients; Clear requires confirmation and writes a disabled tombstone. `Status` opens the factory calibration information; long OK returns to its lead-menu row. `Back` or long OK from the lead menu returns to the main menu. Browsing does not capture, modify the profile or require mutation permission. The prior bound profile remains in use while an unsaved candidate is collected. After save, reboot loads the bound profile without PC/SWD.

This is relative fixture compensation, not a replacement for factory RREF/HG calibration. It corrects signed complex series/shunt deltas relative to that factory plane. It is explicitly engineering/unqualified until endpoint observability, range/amplitude invariance, final leads and independent holdouts pass bench checks. A different MCU or factory OSL sequence/content makes it inactive.

Result details use separate bounded rows for range/RET/attempt count, `AVG7/3`, frequency coverage, factory sequence and applied lead sequence. Diagnostics show fresh BAT/NTC values and age, unavailable sentinels for stale data, settings write phase/error and actual lead status. Resource status distinguishes verified header/table CRC from payload validation; a failed mount never claims CRC OK. Menu/edit changes retain the row cache and erase a disappearing save warning without a full-screen redraw. Read-only UART telemetry and Flash backup remain separate from guarded short-OK activation.

Optional supplementary WCRV composition with lead compensation is not qualified. When a compatible WCRV store is active, the UI explicitly disables lead compensation and refuses new/enable actions; stored lead records are retained. The DSP also refuses a supplementary-curve operation on an already lead-compensated result. This prevents a curve from silently overwriting fixture correction while its provenance still claims application. Default PRODUCT has WCRV runtime OFF.

## Charger-connected navigation and rendering throughput (plan 31)

A connected charger inhibits measurements, not normal idle navigation. With otherwise healthy evidence, startup reaches READY and normal menus/settings remain accessible. The READY footer resolves USB-connected and unplug-to-measure copy from the selected external language catalog; it does not claim that charging current was measured. Short measurement clicks are consumed without deferred activation. USB removal never starts a measurement. Insertion during an acquisition still aborts and drains hardware ownership. Hard faults, residual and unknown/critical supply evidence retain priority; native lead endpoint captures also remain inhibited.

Resource API 5 externalizes the recent lead, diagnostics and result-quality labels in both EN and PT-BR. A small emergency/recovery vocabulary and technical format tokens remain internal. All personal splash bytes and its 3-second hold remain unchanged. Glyph rendering uses one rectangle per character and row-major streaming; window command groups use one CS interval. Existing row caching remains active for menus, editors, diagnostics and lead progress. SPI clocks, acquisition quiet ownership, DMA and static pixel-buffer sizes do not change. Physical responsiveness/visual acceptance remains separate from host pixel equivalence.

## Status-page feedback correction (plan 32)

About displays the complete hardware compatibility identity with the small face so it fits the TFT. Previously the medium face overflowed at x=240 and raised a display fault, even while the electrical fault mask was zero; the error path remains checked. Real-font preview tests now explicitly include About, both languages and fallback, instead of treating an unknown scenario as READY.

Diagnostics convert the actual fresh NTC millidegree value into rounded tenths of a degree Celsius, with the selected decimal separator and `°C` (ASCII `C` in emergency rendering). Signed sub-degree values, stale/invalid `n/a` and sample age remain explicit. This presentation precision is not a temperature-accuracy qualification and does not change the experimental NTC coefficients.

On the first unit, non-halting ST-Link reads with user-selected 100% brightness show applied percent 100, TIM3 ARR=999/CCR3=1000, active-high PWM1 enabled, no TIM3 remap and PB0 input HIGH. Thus this state is continuous-high at the MCU, not reduced duty. The owner reports a transistor on the display module but cannot measure LED/VCC now; physical LED input voltage, driver/current and the reset-versus-runtime brightness difference remain REQUIRES_BENCH_VALIDATION. No unverified polarity, voltage, timer or driver change is made.
